# 中文拼音跳转（Chinese Characters Pronounce）

状态：第一版已实现。2026-10-26 更新。

## 目标与已确认范围

在保留原文搜索的同时，通过汉字的拼音找到跳转目标，不修改缓冲区文本，不在编辑器中显示转换后的拼音。

1. 添加独立开关，默认关闭；关闭时不加载拼音词典，原有行为不变。
2. 第一版支持单个汉字的拼音前缀和完整拼音，与英文原文匹配同时生效。
3. 拼音必须从音节开头匹配，不支持音节内部匹配、跨汉字全拼、多字首字母缩写、跨中文和英文的拼音串匹配。
4. 多音字按选定词典收录的全部读音参与匹配，不进行上下文消歧。
5. 第一版限定普通 Flash 跳转的 `exact` 模式。原生 `/`、`?` 搜索、`f/F/t/T`、模糊搜索、Treesitter、remote 模式和用户自定义 matcher 不自动接入。
6. 保留现有多窗口、方向、折叠、标签选择和默认跳到匹配起点等行为。配置字段为 `search.pinyin`，支持全局设置和单次跳转覆盖。

## 匹配示例

假设 `s` 绑定普通 Flash 跳转，以下输入均指启动后的搜索词：

```text
你好，世界
hala ...
这只有角的动物是主角
```

| 输入           | 预期                                             |
| -------------- | ------------------------------------------------ |
| `h` / `ha`     | 匹配 `好`，同时保留英文原文匹配                  |
| `hao`          | 匹配 `好`，不再匹配 `hala`                       |
| `ao`           | 不通过拼音匹配 `好`；原文中的 `ao` 仍可匹配      |
| `nihao`        | 不通过拼音匹配 `你好`；原文中的 `nihao` 仍可匹配 |
| `nh`           | 不通过首字母匹配 `你好`                          |
| `haoA`         | 不将 `好A` 视为跨中英文拼音匹配                  |
| `jue` / `jiao` | 两个 `角` 均为候选，不按语境筛选                 |
| 直接输入 `好`  | 仍按原文匹配                                     |

表格描述匹配语义；交互中，已分配的标签按键仍可触发跳转，不能把标签操作误认为搜索词匹配。

## 标签与跳转位置

已确认跳转目标：中文落在目标汉字，英文落在原文匹配起点。标签位置和跳转位置分别定义。

首版沿用现有默认布局：标签显示在匹配之后，并尊重现有 `label.before`、`label.after`、`label.style` 配置。例如搜索 `ha`：

- `好` 为中文匹配范围，标签在 `好` 后面，默认跳到 `好`。
- `hala` 的 `ha` 为英文匹配范围，标签覆盖后面的 `l`，默认跳到 `h`。

已采用后置方案；中文覆盖布局留待后续。

覆盖目标汉字的评估：

- `lua/flash/highlight.lua` 已支持标签偏移，统一将标签放在匹配起点已有配置基础（例如 `before = {0, 0}`、`after = false`）。
- 若要求仅中文覆盖、英文继续后置，需要识别候选来源，并在渲染时选择不同位置；不是简单修改全局偏移。
- 还需验证窄标签覆盖双列汉字的显示、光标重叠时的标签隐藏、折行和行尾情况。定位改动较小，完整显示验收仍有工作量。
- 不支持跨字全拼，并不意味着后面的汉字不会被遮住：`好好` 中两个字都可能成为独立候选。后置标签可能遮住相邻原文，首版沿用现有显示策略，不为此增加中文专用布局。

## 输入与标签冲突

能够继续扩展当前有效匹配的按键，不得提前成为跳转标签。

- 当 `h` 匹配 `好` 时，`a` 应用于扩展到 `ha`；之后 `o` 应扩展到 `hao`。
- 同时考虑英文原文和所有中文候选的后续合法字母，不能只检查某一个候选或某一个读音。
- 现有 `lua/flash/labeler.lua` 的避让依赖原文正则，现已补充拼音后续输入信息。
- 输入、退格、候选变化时重新计算避让集合，尽量维持仍然有效的标签。
- 标签不足时沿用现有分配原则，不得通过抢占有效拼音输入来提供更多标签。
- 实现时覆盖大小写、`search.trigger`、`search.max_length` 的交互。显式长度上限仍遵循已有语义；默认无长度上限的用法必须允许继续输入完整单字拼音。

## 多音字策略与数据依据

第一版采用全部收录读音匹配、去声调后读音去重、同一位置候选去重。全部读音指选定词典的收录范围，不宣称涵盖所有历史、方言或姓名读音。

例如 `好` 的 hǎo/hào 归一化后只有 `hao`，不会增加匹配入口；`角` 的 jiao/jue 则提供两个入口，但一个位置始终只显示一个候选。输入 `jue` 可能匹配语境中读 jiao 的字，这是本版有意接受的行为。

### 文献调查（2026-10-26）

[g2pM，INTERSPEECH 2020，第 3 节及表 2](https://www.interspeech2020.org/uploadfile/pdf/Tue-1-7-1.pdf) 对中文维基百科语料进行统计：

- 去掉非汉字后，约 3.63 亿汉字字次、17,720 种汉字。
- 按 CC-CEDICT 判定，762 种为多音字，占字种的 4.30%。
- 这些字出现约 6,700 万次，占字次的 18.49%。

这说明多音字在中文正文中并不少见，应作为正常使用场景处理。该统计包含仅声调不同的读音，不能直接当作本功能的额外候选率，也不能推导任意编辑器单屏出现多音字的准确概率。屏幕字数、文体、代码与中文比例都会影响结果，文本也不是独立随机抽样。

尚未找到可直接用于本功能的“单屏无声调异读字出现概率”数据。后续应在中文正文、技术文档、代码注释等代表性样本中，按可见窗口记录：

1. 去声调后仍有多个不同拼写的汉字出现次数。
2. 不同长度查询前缀对应的候选数量和可用标签数量。
3. 有人工语境标注时，才统计因其他读音引入的额外候选比例。
4. 词典加载、首次搜索及连续按键的耗时。

是否引入上下文消歧，应根据实际候选干扰情况决定，不能仅由多音字字次比例决定。

## 数据来源与第三方库

第三方库可以考虑；“使用第三方资源”和“运行时使用本地词典”并不冲突。

已采用方案：启用拼音功能的用户通过 lazy.nvim 的显式 `build` 钩子，在安装或更新时将固定版本的第三方字音数据转换为完整的本地 Lua 词典。`data.lua` 不再提交到仓库，而是加入 `.gitignore`。这仍然生成完整字库，不是少量测试数据。

示意流程：

```text
固定版本的上游字音词典
  → 解析每个字的全部读音
  → 去声调、处理 ü、去重
  → 安装时生成本地 Lua 数据（不纳入 Git 跟踪）
  → 用户启用功能时延迟加载
```

例如输出结构可为 `角 → {jiao, jue}`、`好 → {hao}`；实际生成数据按音节分组保存汉字，运行时延迟建立反向读音索引。

| 方案                                  | 适用性与取舍                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------ |
| 直接使用第三方字音数据生成 Lua 词典   | 已采用；用户构建时需要 Python 3.9+ 和网络，运行跳转时无需额外依赖           |
| 开发时使用 pypinyin 等库导出 Lua 词典 | 可行；仅生成工具依赖 Python，需要保证按单字提取全部读音，避免词组消歧漏掉读音  |
| 运行时依赖 Lua 拼音库                 | 可以评估；需要验证全部读音、数据覆盖、许可证、体积和维护情况，目前未指定具体库 |
| 运行时调用 Python/Node 等库           | 可以实现，但增加用户安装配置、跨进程调用及失败处理成本，首版不优先采用         |

已调查的候选来源：

- [mozillazg/pinyin-data](https://github.com/mozillazg/pinyin-data)：按 Unicode 码点记录字音，支持一字多个读音；提供合并后的 `pinyin.txt`，仓库声明 MIT 许可证。适合进一步评估为生成输入。
- [pypinyin 官方使用文档](https://github.com/mozillazg/python-pinyin/blob/master/docs/usage.rst)：支持 `heteronym=True`、不同拼音风格和 ü/v 转换，也有词组字典行为。因此导出全读音时应逐字验证，不能直接采用整句消歧结果。

已选定 pinyin-data 0.15.0，固定提交和 SHA-256；覆盖 44,440 个字符、426 个规范化音节，生成文件约 186 KB（含版本及完整性校验元数据）。版本、许可证、来源和生成命令见 [词典来源说明](../third-party/pinyin-data.md)。生成文件与测试用的小样本 fixture 分开维护。显式 `build` 配置负责自动生成；不启用拼音的用户无需 Python 或构建步骤。

## 第一版默认值与实现

- 不接受声调符号或声调数字作为拼音搜索语法。
- 用 `v` 表示拼写中的 `ü`，例如 `lv`、`lve`；首版不增加 `u:` 别名。不能把 `ü` 简单归一化为 `u`。
- 英文原文匹配的大小写规则保持不变；拼音分支与现有 `ignorecase` / `smartcase` 规则保持协调，避免大写标签被无条件转小写后抢占。
- 简繁体均按词典中实际存在的码点查询，不做额外简繁转换；未收录汉字仍支持原文搜索。
- 按缓冲区首次建立实际出现汉字的音节索引，以 `changedtick` 判定修改失效，销毁缓冲区时释放缓存。完整缓冲区索引保留窗口外目标、方向和计数查找能力；多个窗口共享同一缓冲区索引。
- 保留原有 Search matcher，在搜索时将原文表达式与该缓冲区内匹配拼音的汉字字符类合并。位置仍由 Neovim 返回原文 UTF-8 字节坐标，不建立虚拟拼音文本。
- 标签避让根据缓冲区索引判断有效后续输入，不针对每个标签重复扫描整个缓冲区。非 exact 模式或自定义 matcher 不进入此分支。

`jump.register` / `jump.history` 默认关闭；如用户显式开启，保存的仍是原始字面查询，原生 `n` 与 `hlsearch` 不扩展拼音。

## 验收场景

- 开关关闭时无词典加载，原有行为不变。
- 单字前缀、完整拼音、英文原文和直接中文输入符合上述表格。
- 不支持的跨字、首字母、音节内部匹配不会意外命中中文。
- 多音字全读音参与搜索；声调归一化及同位置去重正确。
- 连续输入和退格正确刷新候选，`h → ha → hao` 不误触标签。
- 大小写、触发字符、长度上限、候选标签不足时行为可预测。
- 简繁体、未收录汉字、`lv/lve` 按约定工作。
- 多窗口、正反向、计数、折叠、折行、行尾和相邻重复汉字正常。
- 汉字之前存在 emoji、制表符、其他多字节字符时，跳转和高亮范围正确。
- 长行、大量中文、多窗口和编辑后再搜索不产生明显输入卡顿或陈旧候选；记录实际基准后再设定性能门槛。

## 后续可扩展方向

跨汉字全拼、首字母缩写、中文标签覆盖、词语消歧和其他搜索模式接入均不纳入第一版默认范围。

## 使用方式

```lua
-- 在已有 lazy.nvim 插件配置中添加，保留自己的 fork url/branch：
return {
  {
    "folke/flash.nvim",
    build = "python3 scripts/generate_pinyin.py",
    opts = { search = { pinyin = true } },
  },
}
```

已有安装在添加配置后执行 `:Lazy build flash.nvim`，完成后重启 Neovim。其他插件管理器可以在插件目录执行生成脚本。

生成脚本先验证已有文件的格式版本、上游版本、源 SHA-256 和内容校验；符合则跳过下载。`--force` 强制重建；`--source` 支持使用固定版本的本地源文件离线生成。生成先写临时文件再原子替换，失败保留旧词典。

词典缺失或无法加载时只提示一次，并回退到普通原文搜索。修复构建后重启 Neovim 恢复拼音功能；不会在编辑过程中联网下载。不提供自动执行的根目录 `build.lua`，避免给未启用功能的用户引入安装依赖。

## 验证记录

- 拼音匹配测试改用独立小型内存词典，覆盖缺词典回退；全量词典不再是运行 Lua 单测的前置条件。新增生成脚本的跳过下载、版本变化、校验失败和原子替换失败等必要测试。
- 删除生成词典的干净副本中，全部 1,220 项 Lua 测试通过；4 项 Python 生成安全测试通过。首次真实下载生成、再次跳过下载、使用生成词典匹配中文和多音字均验证通过。StyLua 和 `git diff --check` 通过。
- Lua 测试使用本机已有 mini.test / luassert 依赖运行，避免安装额外依赖。
- 性能抽查使用 headless Neovim，40 行及 1,000 行重复中英文正文（每行约百字）：40 行首次启用约 16 ms；暖缓存输入约 1–5 ms，1,000 行重新索引并搜索约 9 ms。这是本机合成样本结果，不代表所有真实文档或硬件。
- 每次缓冲区修改后会重新扫描全文建立字符索引；超大文件或含大量不同汉字的文本仍需进一步实际体验。
